# NEXTBODY 式 PRD 写作规范

用这套规范写出的 PRD 应当可以直接放进 NEXTBODY-HOOP 的 Paper 文件而不显得突兀。参照源:Paper 文件 `01M0SW066YG64X1X6TQA07024T`,页「新版设计」,目录板 `00 · PRD 总目录 Build Order`(nodeId=1BUP-0),屏幕级范例 `01 · 登录注册`(nodeId=QLX-0),Foundation 范例 F0/F2/F6。

## 核心理念

1. **画板即文档,视觉即规格。** 不另写 Word 式文档;手机样机里的 UI 文案本身就是规格的一部分。
2. **每条决策附"为什么"。** 规则后面必须跟理由或出处(审核条款、漏斗数据、被哪块屏逼出来的),否则视为没写完。
3. **没定的事显式标出,不许假装定了。** 用 `!` 待决项,而不是含糊带过或"先按最合理的做"。
4. **"不做什么"和"做什么"同等显眼。** 每块板必须有 NOT IN V1 框,每条带一句不做的理由。

## 文档体系:屏 + 规矩两层

- **屏幕级 PRD(01–13)**:一屏一块板,按用户时间轴排列,板序即开发顺序。命名:`序号 · 中文名 英文名`,如 `08 · 训练详情 Strain`。
- **Foundation(F0–F7)**:全局规矩层——裁决、命名、口径公式、数据同步、服务端契约、合规、交付。屏说长什么样,规矩说数字从哪来、名字叫什么、哪句话不许说。
- **总目录板(00 · Build Order)**:按 STAGE A/B/C/D 分组,每组一句人话(「先把人放进来」「三张详情,每张只回答一句话」),并声明"读它们的顺序就是开工顺序"。
- 屏与规矩冲突时有明文仲裁:**屏上的数与 caption 或右列打架,屏输**;`⚠️` 标注 > caption > 屏 > 右列。

## 屏幕级 PRD 模板:固定四段骨架

### ① 头部

- **眉题**:英文全大写等宽字(Doto),`XX SPEC · 英文名`,如 `AUTH SPEC · SIGN IN & SIGN UP`。
- **大标题**:一句中文断言,说主张不说功能。✅「不设密码,就没有忘记」「出错的时候,不清屏」 ❌「登录注册流程说明」。
- **导语**:2–4 句。先收束范围("登录只做一件事:……"),再用破折号落到设计意图;常用数字锚点("三条路都在 15 秒内落地")。
- **右侧 NOT IN V1 框**:灰色,每条一行 + 括号理由,如 `手机号 + 短信验证码(国内发行时再开)`。

### ② 屏 + 注释卡

每张 390px 手机样机下挂一张注释卡,三件套:

```
01  授权入口 Gate                     ← 等宽编号 + 中英双语小标题
ENTRY · 0 INPUT                       ← 英文参数行(全大写 · 分隔)
冷启动第一屏。三个按钮顺序固定:Apple 在最上……  ← 一段中文设计论证
```

论证段写行为与理由,不写颜色字号(那是屏本身的事)。手机内 UI 文案保留英文原文。

### ③ EDGE CASES · 05

- **恒为 5 个**,编号命名:`1 · WRONG CODE`、`2 · EXPIRED`。
- 每个 = 迷你 UI 示意卡 + 一段规则说明。
- 导语先给共性结论,再给唯一共同规则:"这五种情况占了登录漏斗里几乎全部的流失。共同的规则只有一条:已经输进去的邮箱和数字,任何错误都不许清空。"

### ④ 收尾双栏

- 左栏「×× · 硬规则」:01–NN 编号条款(见下文条目写法)。
- 右栏「上线前必须成立」:`!` 前缀的准入条件/红线,末尾固定带**埋点清单**(等宽字事件名,如 `AUTH_CODE_SENT · AUTH_DROP{STEP}`)和**验收线**。

## Foundation 板模板:以表为中心的五段式

Foundation 不画屏。骨架:

1. **头部**:眉题 `FOUNDATION · F2 · ONE CALENDAR, ONE FORMULA, ONE VERSION`;断言式大标题(「十条裁决,之后不再讨论」「一个数只许有一个算法」);导语第一句交代读者与动机("这块板的读者是代码代理,不是设计师");右侧挂 NOT IN V1 / SUPERSEDED 声明框。
2. **编号章节**:`01 · THE CALENDAR — 一天从 04:00 开始`,即"序号 · 英文大写名 — 中文副题",节首一小段说为什么需要这节。
3. **正文用表**,每张表有专属列模型,按用途选:
   - 裁决表:`NO / THE QUESTION / THE RULING / LANDS ON`(落到哪几块板)
   - 公式表:`SYMBOL / INPUT FIELDS / FORMULA / UNIT·ROUND / IF MISSING / VER`
   - 冲突表:`一方说 / 另一方说 / THE CALL`
   - 错误像素表:`屏上是什么 / 为什么错 / 该做成什么`
4. **裁决条目**:先一字结论再给理由——"不做。""不收。""接。",然后解释。
5. **收尾双栏**:同屏幕级(硬规则 + ! 待决项 + 埋点 + 验收线)。

## 语言风格规则

- **中英分工严格**:论述正文全中文;UI 文案、枚举、事件名、符号、方法名保留英文不翻译(UNLOGGED、calc_version、AUTH_CODE_SENT)。
- **立法体口吻**:高频禁令词——"只准、不许、绝不、永不、写死、作废、降级"。✅「不允许两个码同时活着」 ❌「建议不要同时存在两个验证码」。
- **破折号"——"高频**:前半句立规则,后半句给理由。"锁在服务端,——不是只把前端按钮变灰。"
- **数字即论证**:能量化的必须量化("15 秒""P50 ≤ 45 秒""≥ 92%""5 的倍数");常数给出来历("−380 是被 09 屏逼出来的")。
- **概念唯一命名**:一个概念只准有一个名字,出现第六个同义词就是 bug。
- **口语狠话收束**,少量、用在刀刃上:"给三条等于没给""别编一个百分比出来"。
- 设计与实现冲突处用 `⚠️` 标注"照屏做会踩坑"的最高优先句。

## 条目与条款写法

- **硬规则**:等宽编号 `01/02…` + 一段陈述,先规则后理由;不加粗前缀、不用冒号领起;条目间可交叉引用("见 R04")。
- **! 待决项**:琥珀色 `!` 前缀;规则是"遇到 ! 号只有两个合法动作:跳过,或回来问。不许实现、不许搭架子、不许『先按最合理的那种做』"。
- **埋点**:事件名等宽字整段照抄,写清"缺一个这条漏斗就读不出来"。
- **验收线**:以「验收线:」开头 = 量化阈值 + 归因句式。✅「验收线:配对完成率 ≥ 92%,01 屏到成功屏 P50 ≤ 45 秒。第三条掉下来是成功屏做错了,不是用户的问题。」阈值必须可机器检查,归因必须预先指给具体环节。

## 写作检查清单

写完一块板,逐条过:

- [ ] 大标题是断言句,不是功能名?
- [ ] 有 NOT IN V1 框,且每条带不做的理由?
- [ ] 每张屏的注释卡都有编号 + 中英标题 + 英文参数行?
- [ ] EDGE CASES 恰好 5 个,导语给了共性规则?
- [ ] 每条规则都附了"为什么"?
- [ ] 没定的事用 `!` 标出,没有含糊带过?
- [ ] 埋点事件名齐全、等宽字照抄?
- [ ] 验收线量化、可机器检查、带归因("掉下来是 X 做错了,不是用户的问题")?
- [ ] 全文没有同义词漂移(一个概念一个名字)?
- [ ] 数字都有单位、阈值都有方向(≥/≤)?

## 例句库(风格锚点,逐字摘自源文件)

- 「登录只做一件事:把这条手环和一个人绑起来。」
- 「未知永不退化成 0:数据层写 null,屏上写 ——。FASTED 的 0 是断言,UNLOGGED 的 null 是沉默,两者在任何一层都不许互换。」
- 「这两张卡不做骨架屏、不做加载态。上一次的结算值一直挂在那里,新值到了就换掉。首屏没有转圈的东西。」
- 「对不上时整块换成 —— 并上报,宁可不显示,也不显示一个凑出来的数。」
- 「哪一段没回来就停在那里,不允许用动画把它补满。」
- 「它给的数必须跟顶上的目标闭合(12.4 + 2.1 = 14.5);只给一条,不给列表,给三条等于没给。」
- 「没有 recompute_log 的批量 UPDATE 视为事故。」
- 「做不到就是这块 F0 没落地,不是执行的人不认真。」
