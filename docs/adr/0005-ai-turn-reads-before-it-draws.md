# 一轮 AI 分成取证与制图两段，仍是一次模型对话

2026-09-05 用户确认：让模型自己按 query 决定读哪些数据，读完再选图填图。这一段路今天已经存在（想 → 读工具 → 想 → `screen.render`），改动是把它的阶段边界变成机械约束，而不是靠提示词里那句 `READ_FIRST` 自觉。

同一次 `streamText` 调用内用 `prepareStep` 切换 `activeTools`：阶段一只挂读工具，阶段二只挂 `screen.render.*`。模型在阶段二发现证据不够时，允许回到阶段一**一次**，仅此一次。选择在一次调用内分段而不是发两次 HTTP 请求，是因为 F4 已裁决第一版不加传输层，而两次请求要多付一次鉴权、冷启动和失败窗口；选择分段而不是两次独立模型调用，是因为 `prepareStep` 在同一段对话里换工具集，不必重发上下文。`prepareStep` 和 `activeTools` 目前全仓库未使用，`streamText` 是单次调用带全部工具。

绘图工具在阶段二**仍然自己查库填点**。账本 `CAP = 60` 计的是去重后的数字个数，`tools.ts` 的 `record()` 在超限时把返回体的 `points` 二分砍半直到装得下；一条 288 点曲线的 distinct 值远超 60，会被砍到 36 上下。如果强制阶段二只能消费阶段一读到的数，曲线就是残的。审计并不因此变松：`auditFrame()` 只审 `title / sentence / footer / action` 四个文本槽与 `data` 树里的字符串，容差 ±0.05，图上的点本来就不在审计范围内——账本管的是模型写在句子里的数字，不是它画的线。

step 上限定 6（阶段一四步、阶段二两步），不是放宽到 12。成本对调用次数是超线性的：多步工具调用每一步都重发整个上下文，按固定前缀 3k、每个工具返回 800 token 估，八步的累计输入约为一步的 18 倍。给模型更多次机会不是可靠性手段，降级帧才是。现有的 50 秒硬超时与其后的 `batteryFallback()` 保留；快速失败重试（首次失败且耗时低于 20 秒）也保留。

## 尚待确定的边界

两段之间不冻结账本，因为绘图仍自取数，「封盘」在这套填点机制下没有意义。预取的 `source_data` 与 freshness 上下文注入在哪一层尚未核实；若它们拼进 system message，前缀缓存会逐轮失效（见 ADR 0006 对关键词预路由的处理）。`turn/index.ts` 注释与 `docs/prd/F4-server-ai.md` 写的 55 秒预算与实现的 50 秒不一致，需对齐，本决策不推导应该改哪一边。
