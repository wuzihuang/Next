# HOOP 开始给夜晚打分，分在服务端算、按四组拆解、只校准会漂的那两组

2026-09-05 用户确认：睡眠一级卡主位给分数，二级页统一改成日 / 周 / 月三档；先前"不评价夜晚"的立场作废。

这条决定推翻的是一条写在三个地方的产品原则。`ConsentStore.swift:135` 的授权文案原话是「HOOP does not score the night」，`Models/Metrics.swift:211` 的注释是「不算分、不评价」，`CONTEXT.md` 的「睡眠页」条目把「睡眠评分」列进了 _Avoid_。三处必须一起改，而且 `ConsentStore` 那句是**替换不是删除**：用户点过同意的版本承诺了不评价，新版本开始评价了，得有一句新的话顶上说明会打分、算什么、基于什么，否则留下的是一个用户从未同意过的空洞。

分数在服务端每夜结算一次并落 `night_score` 新表，App 只读结果。这不是架构洁癖，是被数据成本逼出来的唯一解。八个输入里六个便宜：时长、深睡、醒来次数、入睡时间在 `sleep_nights`（30 夜 30 行），夜间 HRV 有一张从没被 App 读过的现成表 `public.night_hrv`（PK `(user_id, user_day)`，RLS 对 `authenticated` 已开，服务端 settle 流程一直在自动回填），静息心率在 `reserve_daily.night_inputs` jsonb 里。贵的是另外两个：夜间血氧只有逐分钟的 `oxygen_samples`，一夜三四百行、30 夜上万行，全库没有任何每夜聚合；睡眠呼吸率只存在于 `sleep_nights.raw` 这个 jsonb 里，每夜 30–50KB，`select` 带上 `raw` 就是 1–1.5MB，而 PostgREST 无法只投影 `raw->'respiration'` 而不读整个 toasted 值——同一个查询带不带 `raw` 差约三个数量级。客户端算分意味着每次进周/月档都要把这些拉到手机上。更硬的一条约束是一致性：如果周/月因为拉不动就改用更小的输入集，同一夜会出现两个分——日档 78、周档 84，这不可接受。服务端算把血氧的上万行和呼吸的 jsonb 就地聚合成两个数，两个问题一起消失。落新表而不是往 `sleep_nights` 加列，是因为那张表的语义是"手环说了什么"，派生分混进去之后重算要 `update` 原始表；独立表可以直接重建，也能挂进已有的 `nb.recompute_range`。

四组的拆法是为了让二级页那块拆解能说出人听得懂的话。时长 25%、结构 25%（深睡占比 13–23% 满分窗口、REM 占比 20–25% 满分窗口、醒来次数 ≤1 满分 ≥6 触底，组内 40/40/20）、恢复 35%（RMSSD 40ms 起步、静息心率 55–65 满分带、血氧最低值 ≥95% 满分 <88 触底、呼吸 12–18 满分带）、规律 15%（入睡时间偏离个人中位 ≤30min 满分 ≥2h 触底）。时长与结构一开始是同一组「睡眠量」，REM 确认可得之后拆开——一条把时长和结构捆在一起的横条，说不出「睡够了但结构差」这句话，而那恰好是这个分最值得说的一句。时长本身 7.5h 满分、6h≈70、5h≈50、<4h 触底，超过 9.5h 轻微扣分。REM 之所以在这套里，是因为项目对它的判断在讨论中被推翻了：SDK 头文件在 `parseSleepLine` 的注释里写着「KH系列没有【快速眼动(2)、失眠(3)】两种状态」，据此 `Metrics.swift:236` 的 `remMinutes`（筛 `stage == 2` 求和）应当恒为 0；但 `VitalsReadout.swift:250` 只在分期线非空时才画 REM 段，用户在睡眠页上看到了它，而 `DeviceView.swift:1161` 早就把「REM STAGING · AUTOMATIC PPG ON」写给用户看了。厂商那句注释多半过时或只针对部分型号固件。`VeepooBand.probeAccurateSleepFields` 是为此加的诊断日志，打出 `otherDuration`（SDK 注释为「快速眼动期」的整夜汇总，此前只在总时长为 0 时被拿来凑数，从未被人看过）、`eyeMovementPercent()` 与曲线各 stage 的真实分布。它不再是阻塞项，因为缺项规则本来就兜住了没有 REM 的夜。

校准只作用于恢复组和规律组，时长与结构组永不校准。RMSSD 的个体差异极大——有人常年 25ms 是健康态，有人 70ms——拿人群线去卡这一组基本必错，必须向个人基线迁移；「几点睡算准时」本来就只能相对自己定义。但睡眠量不能校准：一个连续三个月睡 5 小时的人，如果我们体贴地把他的满分线挪到 5 小时然后打 95 分，这个分就在奖励一个坏习惯，并且失去全部纵向意义。校准从第 14 个有效夜开始，14→28 夜之间人群基准与个人基准的权重线性滑动，切换完成前分数旁挂一行说明当前以大众水准为标杆；突然切换会让某天早上分数无故跳十几分。

阈值写死在打分函数里，配 `score_version`，改版即全量重算历史。服务端配置下发听着灵活，实际后果是同一夜在不同时间打开显示不同的分且没有任何痕迹解释，用户只会觉得数据在乱跳。只重算最近 N 天（现有 settle 回溯 14 天）比全量更糟：周档七根柱子里第六第七根用了新算法而柱子上没有标记，月视图混着两代算法，趋势就是假的。

缺项按组内重新归一，UI 上说明基于几项中的几项，只要那一夜有记录就必定出分。用中性值填充是最危险的做法，它把一个信息量减半的分伪装成完整分；缺一项就不出分则太脆，按现在的数据多数夜至少缺一项。恢复组一项都没有时该组整个退出，总分由其余三组按原权重重新归一。完全没戴的夜不出分，沿用 `NO NIGHT YET`。缺项说明只出现在二级页的拆解块，一级卡不提——一级卡是扫一眼的地方，二级页才是解释的地方。

分数只染数字本身，卡片保持 `NB.violet1`：≥80 `optimal2`、60–79 `violet1`、40–59 `compareAmber`、<40 `ember1`。给整张卡换色会违反 `VitalsMetric.swift` 顶部那条规则——一个概念只有一个名字和一个强调色，一张卡从青柠变成青色读起来就是另一个物件。文字档位（优秀 / 一般 / 差）不做：那是在分数之上再叠一层评价，而「差」出现在用户睁眼第一屏是产品事故。

日 / 周 / 月的窗口是**滚动**的（最近 1 / 7 / 30 夜），不是自然周月。自然口径下每周一与每月一号这两档会塌成一两根柱子，用户会读成数据丢了；而数据层本来就按 `user_day` 往回数，滚动是零成本。「日」固定为刚结束的那一夜，不做翻页——再加翻页会让日档与周档职责重叠。三档当时只给睡眠；ADR 0012 把同一套滚动窗口给了 RESPONSE，ADR 0013 把同一套给了 HEART。其余五个 vitals 仍由 `VitalsMetric.timeline` 写死。八个指标的"周"语义仍然不同（步数累加、心率分布、睡眠逐夜、RESPONSE 日均值），所以没有一次全改。燃料页那一句已被 ADR 0014 / Paper 09H 覆盖：热量页现在有滚动三档，月是 28 天、按天平均。训练页那一句已被 ADR 0015 / Paper 08C 方案 A 覆盖：训练页现在有滚动三档，月是 30 天，英雄永远是一天的 0–21。

## 尚待确定的边界

`otherDuration` 的真实取值尚未测量，`probeAccurateSleepFields` 的日志还没有跑过一次真机。REM 占比若在多数夜为 0，结构组会长期靠深睡与醒来次数两项归一，届时 40/40/20 的组内权重需要重估。`night_score` 的 migration 需要用户 push——本仓当前会话没有 DDL 权限。夜间血氧与睡眠呼吸率的每夜聚合是新写的服务端函数，两者都还没有任何历史回填，首次上线时更早的夜在恢复组上会长期缺两项。`reserve_daily.night_inputs` 里的静息心率是服务端 `round()` 过的整数，比 `night_hrv.rmssd_ms` 的 `numeric(6,2)` 粗一档，若发现整数化在 55–65 满分带边缘造成跳变，需要改为直接调 `nb.night_rhr`。逐夜的夜间 HRV 趋势图（周/月档把恢复组画成折线）明确不在本次范围内：它需要第二条历史链路，而「最近哪一组在拖后腿」已由周/月 Hero 的短板脚注用一句话回答。

## 一次已发生的回归

第一版 migration（`20260905100000`）为了加一行 `refresh_night_score` 而重新声明了 `nb.recompute_range`，抄的是 `20260903120000` 里的定义——而那份定义早已被 `20260904085910` 取代。推上生产后它回滚了可复现结算的全部工作：`nb.calculation_work` 的行锁（让并发调用等待而不是发布陈旧输出）、dirty range 及其 385 天护栏、当天已在此 tick 与 profile revision 下结算完成时的跳过、以及 revision 三列所依赖的 `calculation_as_of` / `input_revision` / `profile_revision` 三个 set_config。`20260905100001` 逐字恢复了 `20260904085910` 的函数体并只加那一行。

教训写在这里而不是只修掉：**在这个仓库里 `create or replace` 一个已有函数之前，必须先 `grep -l "function <name>" supabase/migrations/*.sql` 看它最后一次是在哪个版本里被定义的**，因为同一个函数在四个 migration 里出现过，而按文件名排序最靠后的那个才是真相。

## REM，实测之后

`probeAccurateSleepFields` 在真机上跑过了，结论推翻了本文前面那段基于 SDK 注释的推断，并且比"有"或"没有"更具体。2026-09-05 那一夜 `accurateType 1`，`otherDuration` 83 分钟、`eyeMovementPercent()` 15%、曲线里 `2:83` 确实存在；紧邻的 09-04 与 09-03 两夜 `accurateType 0`，三项全为零、曲线只有 `0:` 与 `1:`。三夜的设备级 `VPPeripheralModel.sleepType` 都报 1，所以那个字段不是判据——**判据是每条睡眠记录自己的 `accurateType`**。SDK 头文件里「KH系列没有【快速眼动(2)、失眠(3)】」那句只对普通睡眠记录成立。

由此修掉一个已经存在的缺陷：`VitalsReadout` 原先只要分期线非空就画 REM 段，于是 `accurateType 0` 的夜会出现一条 `REM 0M` 的零宽带。那是在用一张图告诉用户他没有 REM 睡眠，而手环说的是它没在测。REM 与清醒两段现在只在分钟数大于零时才进占比条，周/月窗口的做法一致。

REM 进分数的决定不变，缺项归一规则本来就是为这种夜准备的：`accurateType 1` 的夜结构组按深睡40/REM40/醒来20 打分，`accurateType 0` 的夜 REM 退出、组内按深睡与醒来重新归一。


## 2026-09-06：分数必须带着输入证据一起展示

真实夜晚回放发现旧版把跨段清醒空窗中的样本纳入恢复组、把同一结束时间的错日副本计入趋势，并用睡眠夜数代替各生理指标的有效基线夜数。`sleep-v1.2` 保留现有曲线及四组名义权重，改为按记录中合并且裁剪后的睡眠区间取样，以醒来日期识别有效夜。原始错日记录保留，派生评分拒绝它，包括后续重复同步。

HRV 优先使用睡眠记录的原生逐分钟序列；明确的空序列表示没有测到，仅在字段缺失的旧记录上回退五分钟样本。重复时间戳不增加样本数。HRV 至少需要两个独立十五分钟桶，其余恢复指标至少两个不同时间戳才参与计算；这些是防止单点被当成整夜结果的工程下限，并不是临床有效性标准。HRV 和静息心率分别统计此前二十八夜中有效输入的夜数，分别计算个人基线及 14→28 夜的校准权重。

时长仍采用设备报告的记录分钟数，包含记录内清醒分钟；不把分段之间的空窗补成睡眠。服务端同时输出记录时长、外层跨度和空窗长度，使这个既有口径可核查。UI 显示缺组后真正参与总分的权重、每项样本数、采样覆盖率和最长缺口；高分不能被解读为数据完整。HRV 图的刻度覆盖实际峰值，规律图使用服务器提供的同一基线。周/月展示四组的逐夜中位数，明确总分是逐夜总分的中位数，不是组中位数的加权和。

评分随普通同步和历史同步结算刷新，并进入账号隔离的本地快照。网络失败保留旧分并显示刷新失败；加载、无记录、缓存和失败状态不再混用。同账号更新请求及跨账号迟到请求都不能覆盖较新的结果。
