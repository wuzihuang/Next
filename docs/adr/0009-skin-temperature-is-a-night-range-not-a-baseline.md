# TEMP 卡对着本人的夜间范围说话，白天皮温只记录不判定、不进训练负荷

2026-09-05 用户确认。起因是页面对一个健康的人说「高于基线 +1.3 °C」：基线取的是睡眠窗口的均值，英雄位却拿白天最后一个 tick 去比，腕部皮温白天暴露在环境里本来就比被子下低 1–2 °C，两个不同状态的数被放在一起，一个常量 ±0.3 就把它染红了。问题不在基线算错，在「一个点 + 固定容差」这个形态本身。

决定是三件事。第一，结论只在夜与夜之间做：昨夜均值对着本人最近 28 天里最后 14 个有效夜的中位数 ± 2·MAD，半宽地板 0.2 °C，至少 5 夜才出结论（门槛与 RESPONSE 卡的五个有效天对齐）。选 MAD 而不是 sd，是因为一晚戴松了会把 sd 撑爆而对 MAD 几乎无感；地板是因为一个极稳定的人会把范围收成 ±0.1，又回到一出线就红。第二，白天的 tick 继续收、画曲线、出 24H LOW / HIGH 和昼夜差，但不进任何判定；首页小卡和详情页英雄位从醒来起一直显示昨夜的结论，半夜不出「今晚到目前」——半截夜的噪声太大，也没人凌晨三点要一个结论。第三，白天皮温不进训练负荷、不进 STRESS。这与 ADR 0004 拒绝白天 HRV 进负荷是同一条理由：腕部皮温在运动开始时先因血管收缩下降再回升，热天由环境和出汗蒸发主导，目前没有任何依据说它与负荷单调相关。先把白天均值、范围、昼夜差算对并通过 data-read 暴露给 AI 引用，攒够真实数据再议是否进公式。

范围先在客户端算，照 `MealResponseIndex` 的路子做成纯计算 struct 由 `NextBodySyncCoreTests` 覆盖，`VitalsReadout` 只排版。它现在只服务这一张卡，AI 读的是原始 tick 自己能算；要进 night score 时再搬到服务端与 ADR 0008 同批结算。

随之退场的常量：`FIXED ±1.0 °C` 的 gauge、`STABLE ±0.3 °C` 的参考带、首页火花线写死的 35.5–37.0（那是核心体温的刻度，皮温整条线贴底）。「基线」一词从这张卡和 `tempBaseline` 的命名里一起退场。
