# 所有 AI 输入只走一条显式 workflow

2026-09-05 用户裁决：删除旧架构，统一为「先校验次数与金额额度 → 模型自主选工具读取 → 根据读取结果输出图表」。本裁决更新 ADR 0005 的 SDK 自动分步方案及 F4 中独立估餐、关键词预路由的旧约定。

## 执行边界

文字、图片都进入 `/turn`。语音保留独立的 ASR 传输，转写与随后的 `/turn` 共用一个 operation UUID。服务端先验证身份、同意、输入、重放与租约，再校验次数和金额；健康读取工具继续使用用户 JWT，只有计量 RPC 使用服务身份。

同一个用户操作只消费一次次数，底层调用分别记成本。同一端点最多准入两次，限制操作 ID 被重复利用；成功回答沿用 turn/frame 的幂等重放。额度每日补10次、累计最多20次，金额按数据库用户日与价格表计算。每个模型步骤前重新检查金额，ASR 记录实际提交音频秒数。金额目前检查已结算费用，不是并发在途金额预留；供应商遗漏用量的账单补偿也尚未实现。

读取阶段开放健康工具、模型主动选择的 `image.inspect` / `meal.estimate`，以及 `workflow.ready`。模型根据问题和历史自行决定指标与日期，不做客户端或服务端关键词分流。证据足够即可 ready，四步是取证上限。ready 可以指定输出使用的 from/to，服务端只校验格式与范围，不推断语义。

输出阶段只开放绘图工具和最多一次 `workflow.reread` 控制。补读与绘图不能在同一步竞争执行；每步最多接受一次绘图。整轮最多六个主模型步骤、共享50秒模型工作截止时间。通用 Chat 仍可直接回答，无需为常识或算术读取个人健康数据。

## 首页闲聊交接到 Coach

2026-09-08 用户裁决：首页识别到 personal / small talk 时，自动打开 AI Coach，保留用户原话与附图接着聊，不输出「超出范围」拒答。模型通过 `workflow.coach` 按语义选择交接，客户端不做关键词分类；健康数据查询、估餐和设备操作仍走原流程。

交接在同一次 `/turn` 内切换到 Coach 对话规则，沿用 operation UUID 与次数准入；各模型步骤分别计成本。客户端收到 `coach.handoff` 后把原话放进预留的聊天记录，展示这次请求后续的进度和回答，不另发一次请求。终态保存交接标记，重放和手机工具续跑都能恢复 Coach 去向，后续追问沿用同一 conversation ID。

## 为什么显式逐步执行

真实 `ai@4.3.16` 测试证明，其自动多步流会在消费侧 `onStepFinish` 完成之前开始下一次供应商请求。只在回调中修改 activeTools，无法保证「先结算、切阶段，再调用」，渲染成功后也可能额外启动一步。

现在每次 `streamText` 固定 `maxSteps:1`，服务端保存同一段消息历史，等待本步完成与用量落库后才执行下一步。客户端仍是一次 HTTP/SSE；没有增加 MCP 或第二次客户端请求。每一步仍发送上下文，因此不能把“一次 workflow”解释为“一次供应商调用”。

## 删除的路径

- 首页餐食关键词分类与医疗关键词短路。
- 根据提问语言猜日期、选数据源、裁剪图表工具的预路由。
- 本地150次额度计数与 DEBUG 客户端模型直连。
- 自动图片预处理模型调用与首页照片直达独立估餐。
- 独立 `/meal` 的生成逻辑、后台旧估餐任务自动重试；旧端点仅返回410迁移错误。
- `screen.last` 将历史屏帧再次读给模型的旧工具。

餐食估算是模型选择的读取工具，返回明确标记的估算草稿。食物卡使用该草稿的营养字段，确认按钮提交现有草稿，不再调用模型、不自动保存。旧待估餐队列保留原始内容并提示重新发送，避免迁移时丢失用户记录。

## 验证与部署

真实 SDK 配合假供应商覆盖阶段顺序、无额外模型步、完整用量、模型选择图片/餐食工具、范围选择与拒绝门禁；数据库测试覆盖可信权限、跨入口次数、用户日和金额；客户端经过模拟器构建。

必须将可信计量迁移、函数和客户端作为同一版本交付。先验证迁移和服务端，再发布客户端；旧 `/meal` 被退役后旧客户端估餐不再可用。本地改造不表示线上已部署。
