# AI 生成计划、跨会话记忆、手机执行动作，仍然是同一条 workflow

2026-09-06 用户裁决。三件事扩展 ADR 0011 的「一条 workflow」为「读 → 执行 → 输出」三步，并撤销 S10「只有只读工具」：模型可以调用有副作用的工具，执行在手机上，结果回到同一轮里。

## 计划

计划页不再由手机本地规则拼（撤销 `PlanFaceMath` 的「No /turn」）。用户当天第一次上滑，手机打一次 `surface=plan` 的 `/turn`，思考流在计划页上打出，模型输出一句标题、一句总结、三到五条自由拟定的任务；结果存 `daily_plans`（按 user_day 一行），同一用户日再上滑直接读表，「重新生成」才再打模型。占用户额度，和其他 turn 一样。

不做夜间预生成：预生成拿不到早晨结束的那一夜。不固定任务槽位：固定槽位会让模型在没有对应数据的日子编一格。

计划的输入是可枚举的，所以 plan surface **不走四步读阶段**：服务端在请求时固定预取过去三个用户日的负荷、睡眠分、电量、餐、前一天的勾选记录，加上记忆，一次模型调用出结果。这是 ADR 0011 的例外，理由是成本：四步读的累计输入约是一次调用的十五倍（ADR 0007），而计划每天都要生成一次。

对勾是用户手动的完成标记，写 `plan_task_checks`，不调模型。第二天生成时模型同时看到勾和数据，可以说「勾了早睡但 1 点才睡」，但不替用户打勾。

## 记忆

一次会话（Chat 或首页语音 / 拍照，退出 Chat 或三十分钟无 turn 即结束）结束时，服务端用一次模型调用把旧记忆和本会话合并重写为两层文字：概述段落加带日期和来源的事实条目，封顶约 1500 token，模型可以删过时的条目。存 `user_memory` 一行一人。每个 turn 和每次计划生成把它拼进上下文。

总结调用不占用户额度，只受「每会话一次」限制，因为用户没有点任何东西。记忆对用户可见、可整段删除，撤回同意或删号时清空，因为它是从健康对话里提炼的个人数据。

记忆不是上一轮的数字。S2「上一轮的数字不能带到这一轮」仍然成立：记忆写的是「膝盖有旧伤」「不吃乳制品」这类事实，不是「昨天心率 62」。

## 动作：turn 模式的手机工具

2026-09-06 第二次裁决，取代同日第一版「动作只做终态」的写法：**所有有副作用的工具都是 turn 内的工具调用，有明确返回值**。用户要知道闹钟到底设成没有，终态意图给不了这个答案。

模型跑在边缘函数里，碰不到蓝牙，所以执行在手机上，传输用**可续 turn**：模型调到手机工具时，服务端发 `tool.request` 事件，把消息历史、workflow 状态和待办调用存进 `ai_turn_states`，关流；手机执行（该确认的弹确认，60 秒不点算 `CANCELLED`），带同一个 Idempotency-Key 再 POST `/turn` 附上结果，服务端从存档续跑。选可续而不是服务端轮询等结果，是因为 Supabase 每个请求可能落在不同实例，内存里等不到；不换 WebSocket，是因为客户端和函数都不用换传输层。一轮最多续 3 次，等手机的时间不计入 50 秒模型预算，每次续跑重新起表。

三步 workflow：读 → 执行 → 输出。执行阶段完成后允许回读一次（同步完再读今天的数据），复用 `workflow.reread`。plan.render 是输出工具，任何入口都能调；结果落 `daily_plans`，Chat 里显示一张指向计划页的卡。

手机不在场（后台、手环未连）时工具返回 `APP_BACKGROUND` / `BAND_DISCONNECTED`，模型如实说，不排队、不重试。排队执行是推送提醒的变体，而推送本期不做。

设备状态（电量、连接、闹钟）随 turn 上传作为第一步的读证据，不让模型为此回调手机。

不起 MCP 服务器。F4 的裁决不变：工具定义在边缘函数内，用户 JWT 下走 RLS。「MCP」在本决策里只是「更多工具」的口语。

## 不做的

推送提醒。计划页词条的「推送督促」仍在 _Avoid_ 里。
