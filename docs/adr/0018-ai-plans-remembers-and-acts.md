# AI 生成建议、跨会话记忆、手机执行动作，仍然是同一条 workflow

2026-09-06 用户裁决。三件事扩展 ADR 0011 的「一条 workflow」为「读 → 执行 → 输出」三步，并撤销 S10「只有只读工具」：模型可以调用有副作用的工具，执行在手机上，结果回到同一轮里。

## 建议（2026-09-08 取代每日计划；2026-09-09 部分被 ADR 0022 取代）

> ADR 0022：一个用户日一份当日建议，当天第一次打开并同步后由手机点火、服务端脱离连接跑完；打开只读，同一天只有 REFRESH 才重生成。下面「每次完成打开都发起新 turn」「不做每日缓存」的写法自此作废，其余（证据、去重、审计、空数组）不变。

用户撤销「每天生成一份计划、同日缓存、任务打勾」。现在每次完成打开建议页都发起新的 `surface=plan` turn，依据最新数据输出按相关性排序的一到五条编号建议；缺少可行动证据时允许空数组并如实说明。关闭不取消未完请求，生成中重开复用该请求。失败保留上次内容时必须明确标旧。每次新生成占用户额度，网络重试仍复用操作 ID。

每条围绕一个具体指标，说明「有时间的读数/比较 → 现在能做什么 → 为什么」。不再分运动/三餐/同步等固定槽位，不生成全天排程、不为凑够五条编建议。长内容完整展示，去掉勾选和完成评价。协议的 `plan`、`tasks` 和表 `daily_plans` 保持兼容；表中一行是当天最近一次建议，供下一次去重，并非缓存命中。历史 checks 保留但不再参与生成。

建议入口继续预取证据，沿用同一模型和 workflow。先完成需要的结算，再读过去十四天及今天的数据；读取前后检查计算版本，剔除未结算的派生值。只将最近两天的负荷、身体电量、夜间 HRV/RHR、记录蛋白、最近完成的睡眠，以及有持续新读数的滚动压力窗口作为可引用证据。历史天用于计算个人比较（至少五个先前完整日），不是拿今天的部分负荷对比全天。记录蛋白明确是已记录量，不证明用户实际吃得不足。压力需要多次最近腕上读数，早先的滚动日中位数不冒充长期个人基线。

模型看到当天最近一组和前一天的建议，用于挑选不同的有效做法；不能为新鲜捏造异常或反转仍合理的意见。输出必须带本轮证据 ID 与参考资料 ID；服务端拒绝无依据、重复核心信号、整组照搬、指定废话模板以及超长不完整内容，允许模型在同一 turn 修正。所有可见数字（包括行动文字）核对引用证据，旧建议、URL 和 ID 不进入数字账本。

建议使用独立的写作规则，撤销该面继承的面板「禁止建议」与短槽限制。专业知识由有日期的已核实资料提供：

- [NIH ODS 运动营养](https://ods.od.nih.gov/factsheets/ExerciseAndAthleticPerformance-HealthProfessional/)：充分蛋白与运动后修复；不从疲劳推断缺乏，不追加任意摄入目标。
- [NIH NHLBI 睡眠习惯](https://www.nhlbi.nih.gov/health/sleep-deprivation/healthy-sleep-habits)：结合实际睡眠调整作息、晚间光线和咖啡因。
- [NIH NCCIH 放松方法](https://www.nccih.nih.gov/health/relaxation-techniques-what-you-need-to-know)：舒适慢呼吸与肌肉放松；不承诺手环压力指数下降。
- [ACSM/ECSS 训练与恢复共识](https://onlinelibrary.wiley.com/doi/10.1080/17461391.2012.730061)：训练需有恢复，不凭单一手环指标诊断过度训练。

上述资料于 2026-09-08 核对，来源链接由服务端白名单附加并保存在建议项里。超出该资料范围的外部事实仍需联网，检索不发送私人健康记录。客户端、`turn` 与允许零条建议的数据库约束迁移需配套发布；本地验证不表示已部署。

## 记忆

一次会话（Chat 或首页语音 / 拍照，退出 Chat 或三十分钟无 turn 即结束）结束时，服务端用一次模型调用把旧记忆和本会话合并重写为两层文字：概述段落加带日期和来源的事实条目，封顶约 1500 token，模型可以删过时的条目。存 `user_memory` 一行一人。每个 turn 和每次计划生成把它拼进上下文。

总结调用不占用户额度，只受「每会话一次」限制，因为用户没有点任何东西。记忆对用户可见、可整段删除，撤回同意或删号时清空，因为它是从健康对话里提炼的个人数据。

记忆不是上一轮的数字。S2「上一轮的数字不能带到这一轮」仍然成立：记忆写的是「膝盖有旧伤」「不吃乳制品」这类事实，不是「昨天心率 62」。

## 动作：turn 模式的手机工具

2026-09-06 第二次裁决，取代同日第一版「动作只做终态」的写法：**所有有副作用的工具都是 turn 内的工具调用，有明确返回值**。用户要知道闹钟到底设成没有，终态意图给不了这个答案。

模型跑在边缘函数里，碰不到蓝牙，所以执行在手机上，传输用**可续 turn**：模型调到手机工具时，服务端发 `tool.request` 事件，把消息历史、workflow 状态和待办调用存进 `ai_turn_states`，关流；手机执行（该确认的弹确认，60 秒不点算 `CANCELLED`），带同一个 Idempotency-Key 再 POST `/turn` 附上结果，服务端从存档续跑。选可续而不是服务端轮询等结果，是因为 Supabase 每个请求可能落在不同实例，内存里等不到；不换 WebSocket，是因为客户端和函数都不用换传输层。一轮最多续 3 次，等手机的时间不计入模型预算（面板与 Chat 80 秒（2026-09-09 起，原 55 秒放不下联网核实的报餐），建议面 110 秒——ADR 0022），每次续跑重新起表。

三步 workflow：读 → 执行 → 输出。执行阶段完成后允许回读一次（同步完再读今天的数据），复用 `workflow.reread`。plan.render 是输出工具，任何入口都能调；结果落 `daily_plans`，Chat 里显示一张指向计划页的卡。

手机不在场（后台、手环未连）时工具返回 `APP_BACKGROUND` / `BAND_DISCONNECTED`，模型如实说，不排队、不重试。排队执行是推送提醒的变体，而推送本期不做。

设备状态（电量、连接、闹钟）随 turn 上传作为第一步的读证据，不让模型为此回调手机。

不起 MCP 服务器。F4 的裁决不变：工具定义在边缘函数内，用户 JWT 下走 RLS。「MCP」在本决策里只是「更多工具」的口语。

## 不做的

计划页的「推送督促」仍在 _Avoid_ 里。手机系统通知改由 [ADR 0019](0019-notifications-fire-on-edges.md) 管，不再是「本期不做」。

## 2026-09-08 · 按需读取与外部事实核实

用户要求设闹钟、找手环、报餐等请求跳过无关的近期健康记录，并要求所有需要外部事实的问题先联网核实。沿用同一条 workflow，由模型按语义选工具，不增加关键词预路由。

- 普通 turn 只上传本机设备状态与待上传数量，不先等待上传、结算。个人数据工具实际被选中时才检查计算与同步状态；云端今天的派生值按需结算。存在本机待上传记录时，读工具要求 `health.prepare` 在手机准备后重读。该工具复用执行权限和续 turn，准备完成仍停在读阶段；准备不成功时保留不完整状态。计划入口继续预先准备。
- `screen.render.text` 和已有草稿的 `screen.render.food` 可在读/执行阶段直接结束，不再为 `workflow.ready` 单独多打一轮。它们不能与读取或手机动作在同一步竞争；个人测量图表仍保留原来的取证与阶段门禁。
- `web.search` 使用千问原生多模态流式接口，强制联网、返回来源。主模型的网关和后备模型不承担搜索协议适配。一次 turn 最多三次实际搜索，相同查询复用结果；用量计入同一个操作，续 turn 保存结果与计数。
- 搜索只发送模型整理的必要公开问题，不自动附上个人历史、记忆、身份或照片。外部事实（包括食品营养、商品、新闻、天气、常识、健康信息）要求先搜网；设备动作、算术和变换用户提供的内容不搜网。来源缺失、流未完成或搜索失败不能声称已核实。
- `meal.estimate.reference_query` 指定公开菜名/商品营养查询；先获得联网参考再估算。照片食物不明确时先辨认。参考资料不能证明份量或变成个人测量；草稿仍需确认，记录动作仍需真实手机结果。
- 来源链接取自供应商返回的 `search_info`，随帧保存，首页和 Chat 提供「参考来源」入口。网页数字只供普通事实文字核对，不注册为个人测量证据。长期偏好仍随新 turn 提供；续 turn 使用保存的上下文，不重复读取记忆、会话摘要或计划证据。

接口依据：[千问联网搜索文档](https://help.aliyun.com/zh/model-studio/web-search)。本改动需要服务端与客户端配套发布，代码验证不表示已部署；新增的 `health.prepare` 需要新版手机执行器。
