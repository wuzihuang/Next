# 手环连接 3 秒目标：实测与优化方案

日期：2026-09-04。阶段：研究与基线测试；尚未实施提速改造，等待方案确认。

## 结论

**正常条件下把常见连接压到 3 秒内有依据，但目前不能承诺每次冷启动都在 3 秒内。** 建议先统一连接入口、拆开与连接无依赖的云端等待、保护验证到首个读取的指令时段，再针对 SDK 握手长尾做独立实验。不要优先改成 UUID 自扫描，也不要把超时直接缩短到 3 秒。

证据有两面：本次新增 12 轮里，从 SDK 开始扫描到完成密码验证并读取新电量，全部小于 2.49 秒；但此前 10 轮里，存在单是连接到验证就耗时 8.42、13.99 秒的情况。新一批较快结果没有消除旧长尾，也不能证明代码已经优化。

此次没有删功能，没有修改正式连接代码、SDK 参数、配对权限或固件。只运行真机实验、阅读实现与官方资料、生成报告。

## 1. 3 秒具体计什么

建议验收目标：**App 收到启动／前台激活事件 → 已绑定手环完成 SDK 密码验证 → 一次新的电量读取成功**。以 monotonic clock/signpost 记录。设备已开机、蓝牙已授权且开启、账号有效、已绑定设备在正常可达范围内。

- `connect step 2` 只是物理蓝牙连接，不能当成业务就绪。
- `connect step 4` 才是 SDK 验证成功；之后还要新读取回执。
- 缓存电量、预先显示 CONNECTED、不再转圈，都不能替代真实就绪。
- 历史同步、能力读取、个人资料同步、后台上传仍全部保留，分别记录完成时间；“3 秒连接”不宣称“全部历史已经同步完”。

现有测试的总耗时从 **Mac 发出 devicectl 命令**起算，包含工具、设备启动和日志传递开销，不能精确等同于手指点图标后的耗时。旧批次每秒检查一次，新批次每 0.1 秒检查一次；阶段耗时使用同一设备日志时钟，不混用两个时钟做时间戳相减。因此当前还没有严格的触屏到就绪 P95。

## 2. 实测结果

设备：iPhone 16 Pro Max，iOS 26.6.1（23G83），Debug 构建，真实 Veepoo 手环。无模拟数据、登录或授权绕过。原始 SDK 日志可能含设备信息，仅在本机临时目录保留；项目内证据只保存计时和结果。

### 2.1 关闭重开：原有 10 轮 + 新增 12 轮

| 测试批次 | 成功 | 启动命令至新电量均值 | 中位数 | 样本 P95 / 最大值 | 严格小于 3 秒 |
|---|---:|---:|---:|---:|---:|
| 原有 10 次，1 秒观察粒度 | 10/10 | 6.44 秒 | 5.05 秒 | 17.07 秒 | 0/10 |
| 新增 12 次，0.1 秒观察粒度 | 12/12 | 3.504 秒 | 3.293 秒 | 4.304 秒 | 1/12 |

两批均无连接 deadline 超时。两批观察粒度、运行时段、设备和缓存状态不同，**差值不能当作某种优化的收益**。样本 P95 使用 nearest-rank；12 个样本的 P95 就是最大值，不是生产总体的保证。

新增实验交替进行：上轮读到电量后，让原 App 继续运行 2 秒或 20 秒，再终止并重启。不是让手机／手环关机 2 或 20 秒，也不是修改重连逻辑。

| 上轮新电量后的运行间隔 | 轮数 | 启动命令至新电量均值 | 扫描至新电量均值 | 小于 3 秒（总耗时） |
|---|---:|---:|---:|---:|
| 2 秒 | 6 | 3.283 秒 | 1.655 秒 | 1/6 |
| 20 秒 | 6 | 3.725 秒 | 1.865 秒 | 0/6 |

**没有证据支持“固定多等一会再重连会更快”。** 这不是随机化的射频实验；无法把差异归因于单一设备状态，也不能据此删除恢复等待或重试。

### 2.2 新增 12 轮的阶段拆分

| 阶段 | 均值 | 中位数 | 样本 P95 / 最大值 |
|---|---:|---:|---:|
| SDK scan start → connect start | 0.0013 秒 | 0.0011 秒 | 0.0025 秒 |
| 发起连接 → 物理连接 | 0.0270 秒 | 0.0261 秒 | 0.0377 秒 |
| 物理连接 → SDK 验证成功 | 1.6241 秒 | 1.6892 秒 | 2.3152 秒 |
| 验证成功 → 新电量回执 | 0.1077 秒 | 0.0915 秒 | 0.1364 秒 |
| SDK scan start → 新电量回执 | 1.7602 秒 | 1.8382 秒 | 2.4812 秒 |

这批扫描回调几乎立即返回，所以删扫描路径没有可观的已测收益。`scan start` 在等待 PoweredOn 之后打印，并非 App 创建蓝牙管理器的时刻；这张表不能证明无线发现总成本永远只有 1 毫秒。RSSI 曾返回 0，不能用它推断实际距离／信号质量。

总计时减去扫描后阶段，平均剩余约 1.744 秒，**混合了工具启动、App 启动、调度、授权状态恢复、扫描前等待和可能的网络等待**。目前没有足够的埋点把它全部归为首页网络。若要正常冷启动 P95 <3 秒，以这批 BLE 最慢 2.481 秒看，其他阶段预算只有约 0.519 秒；是否够用需要正式生命周期埋点验证。

### 2.3 旧慢轮次不能忽略

单位秒，起点均为 SDK `connect start`：

| 慢轮次 | 物理连接 | MTU 日志 | 验证完成 | 新电量 |
|---|---:|---:|---:|---:|
| 原第 2 轮 | 0.955 | 4.359 | 13.991 | 14.074 |
| 原第 3 轮 | 0.023 | 6.130 | 8.423 | 8.511 |

第 3 轮物理连接仅 23 毫秒，但 MTU 日志到 6.13 秒才出现。长尾发生在连接后的协议／SDK阶段，减少首页请求或跳过扫描不足以解决。MTU→Pairing 在旧十轮中约 0.302–0.324 秒，可能存在固定调度，但闭源实现不可见，不能断言是可删除的等待。

### 2.4 前后台与页面场景的证据边界

额外执行了一次不依赖 XCTest 点击的系统切换：先完成新电量读取，等初始同步运行 20 秒，打开系统设置使 App 进入后台，2 秒后再启动／激活 NextBody。

- 返回命令成功，原控制台进程仍存活。
- 观察窗口内没有新的连接发起或断连日志。
- **返回后 45 秒内没有新的电量读取成功回执，不能算“返回后新读取 <3 秒”通过。** 窗口内仍有历史处理／上传日志，不等价于链路坏了。
- 可能涉及 `OriginDataSync.inFlight` 合并等待或场景回调触发条件；尚未用专门埋点证明原因。不能把它说成已验证的 SDK 故障或已证明的快恢复。
- 原本的 XCTest 页面压力测试两次都在启用自动化模式时超时，0 轮页面场景真正执行。此次未绕过该系统限制。模拟器也不能替代真实手环验证。

因此已有：22 轮可比较的冷重启、新前后台实验的 1 次基线连接及 1 次返回观察；没有新的页面压力通过结论。

## 3. 各种方法对比

| 方法 | 可以解决什么 | 保留功能的做法 | 收益与风险 | 建议 |
|---|---|---|---|---|
| A. 统一连接入口，云端任务不挡连接 | 启动／前台路径中不必要的串行等待 | 账号、同意、绑定有效后启动单一连接任务；首页数据、上传照常完成 | 有源码依据；实际节省多少尚未 A/B。必须防云端旧电量覆盖刚读到的新值 | 第一优先 |
| B. 从验证前到首个读取统一占用 BLE 指令通道 | 连接完成瞬间被实时测量、同步任务争用；多入口重复工作 | 就绪首读后把通道交回完整测量／同步；运动中保留排他约束 | 存在竞态窗口；未证明是此次长尾的原因。不可并发发送多个 BLE 指令 | 与 A 一起设计 |
| C. 保留进程时复用已验证连接，明确前台“就绪检查” | 切页面／前后台无必要重新握手，或排在历史上传之后 | 同一设备、同一会话保留链接；按 TTL 做轻量真实检查，剩余同步继续 | 理论上最有利于暖启动；此次前台新电量未通过，需要先定位任务合并 | 高优先，单独验收 |
| D. 用状态／扫描回调替代 100ms 轮询 | PoweredOn 与发现后的调度量化 | 同样保留取消、超时、一次性完成和绑定匹配 | 正常理论上合计约 0–200ms；本批 scan→connect 已约1ms，不能承诺秒级收益 | 次要优化 |
| E. UUID 已知设备重连或 SDK auto 模式 | 真正等待广播／扫描的情况 | 只选已绑定设备；单一 SDK 连接模式；完整验证和扫描回退 | Apple 支持 UUID retrieval，但 Veepoo 自扫描会再次扫描，可能更慢；auto 和手动并行曾出问题 | 隔离实验，不作为首选 |
| F. SDK／固件握手长尾优化 | 已物理连接后 MTU、认证、初始化耗时 | 向厂商提供脱敏阶段 trace，寻求正式快恢复／初始化调度支持，保留全部安全与能力逻辑 | 这是覆盖旧8–14秒长尾的关键候选；没有公开开关证明可直接压至3秒 | 必须研究，实施依赖厂商证据 |
| G. 蓝牙状态保存与恢复 | 系统回收／后台后的连续性 | 按 SDK 支持方式恢复 central、delegate、外围设备及完整状态 | SDK公开接口未找到恢复配置契约；不应替换其 manager 或宣称用户强退也有同样保证 | 后续独立项目 |
| H. 主线程、日志和构建模式对照 | Debug 大量日志／启动数据处理争用 | 保留必要诊断；全量 SDK 日志仅诊断时开；业务计算移出主线程，SDK入口留主线程 | 未测 Release 对照，收益未知。需要先 Time Profiler 和相同设备 A/B | 与首批测量配套 |

### A/B 的源码依据与实现约束

- 首页路径在 `HomeView.swift:400–403` 等待 `Repository.bootstrapHome`，之后还可能执行晨间组件操作，才到 `458–460` 的连接／同步入口。
- 前台路径在 `NextBodyApp.swift:44–51` 先等待同意记录和待上传证据，再请求同步。它与首页入口是不同路径；可能先行触发，**不能说每轮一定等完首页网络才连接**。本批多数日志在读电量前没有 bootstrap 完成标记。
- `OriginDataSync.swift:56–64` 在连接成功后才 `LiveReadout.standDown`；连接事件可能先唤起实时测量。需要会话一致的单一通道所有者，不能以“提速”为由并行 BLE 命令。
- `Repository.swift:198–201` 会把云端电量和固件写回本地；提前 BLE 后需要观察时间／会话代际保护，防止晚到旧响应覆盖新数据。
- `OriginDataSync.inFlight` 当前合并的是完整任务，前台返回可加入较长的历史同步；应区分“连接已就绪”“首个新读取”“历史同步完成”，但必须保留原有完整同步和上传。

### 为什么 UUID 快连不是第一选择

Apple 提供按 UUID 找回已知外设的方法，也建议找不到时回退扫描。但“获取到了 CBPeripheral”不等于已完成应用连接或 Veepoo 验证。

本项目 SDK 的 `VPBleCentralManage.h:104–107` 明确禁止混用 self-scan 与普通 connect。官方随包 Demo `VPCustomScanManage.swift:10–12` 更明确说明：自扫描会让 SDK 内部再扫描一次，可能更慢。公开 central header 未找到一个可无条件替代现有路径且保留完整协议的“快速重连”API。不能用 KVC 构造假 model 或直接覆盖 SDK delegate。

## 4. 不删功能的实施边界

1. 保留密码验证、绑定归属、账号／同意检查、系统配对和现有 BT 能力；不为提速关闭任一项。
2. 保留个人资料同步、能力发现、真实电量、全部历史读取、重试、离线证据和上传。仅调整依赖／调度，不丢任务。
3. 保留一次一个原生 BLE 指令、运动排他、主动测量停止与恢复。能力未就绪前不提前开放未知能力入口。
4. 3 秒是性能目标，不是新的失败 deadline。原有正常恢复窗口仍保留；慢连接不能在3秒被强制掐断来美化平均值。
5. 同时保留连接成功率、首读成功率、同步完成率、耗电与后台行为验收；不能只看页面显示速度。
6. 过期登录、未授权、新设备首次确认、手环不在范围内等真实等待单列统计，不能假显示已连接，也不能声称它们同样可保证3秒。

## 5. 建议确认后的执行顺序

**第一步：准确计时 + 统一启动／前台连接调度。** 增加启动、授权恢复、蓝牙 PoweredOn、扫描、物理连接、MTU／SDK阶段、验证、新电量、历史同步完成的分段记录。先区分工具耗时与 App 本身耗时，再实施 A+B；C 的前台合并等待同时纳入定位。

**第二步：保留功能的对照实验。** 同一手机／手环，交替基线与候选构建，各做至少30次冷启动、30次前后台、30轮页面往返。收集真实生命周期到新读取的 P50/P95/max、<3秒比例、成功率、重复连接、取消和掉线。Release／Debug分组，不能混在一张“提速”数字里。先后顺序交替，固定距离并记录电量与设备状态。

**第三步：只对仍存在的长尾做 SDK 实验。** 如果 A+B 之后 connect→verified 本身仍超过3秒，继续删首页请求无效；将 MTU／验证 trace 与厂商正式接口对齐。UUID、自扫描、auto模式各自独立 A/B，不混用；厂商返回建议后再决定 SDK／固件升级。

验收建议：正常已绑定场景先以真实 App 生命周期起点的 **P95 <3秒** 为目标，同时披露最大值和每次超标原因。如果要求“每一次都 <3秒”，目前证据明确不足，必须同时解决协议长尾和不可控无线等待，不能靠只报平均数满足。

首次配对、解绑后重绑、账号切换、断网／过期会话、蓝牙开关、运动中进入页面、完整历史与主动测量均需回归。UI 自动化未启用前，页面覆盖仍是未完成项。

## 6. 推荐决策

先批准 **A+B+C 的测量和小范围实现**，再根据完整阶段数据决定 D/H；E 单独实验，F针对复现长尾推进。现在不建议先换SDK、不建议先改自扫描，也没有依据直接承诺“改完必然每次3秒”。

本次研究已经给出候选方法及基线证据；候选代码收益尚未实测，因为本阶段按要求没有开始正式优化。下一阶段的结果必须来自实际 A/B，而不是上述理论节省相加。
