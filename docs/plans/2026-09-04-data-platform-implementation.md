# 本地、云端与 AI 数据链路实施记录

对应规格：[GitHub #2](https://github.com/wuzihuang/Next/issues/2)。本次代码尚未部署生产；下表描述这次实现后的职责划分。

| 数据 / 场景 | 本地 | Supabase | UI 与 AI 的读取方式 |
|---|---|---|---|
| 新采样、睡眠、RR | SDK 采集后先进入按账号隔离的 SQLite 待上传队列 | 幂等入库、分域确认及缺口状态；RR 保留有序证据 | UI 可展示临时状态，AI 只把云端确认数据当正式事实 |
| 体重、体成分、餐食 | 未确认操作受保护；餐食估算输入也持久化 | 稳定操作 ID、准确 ACK、修改追加、删除标记 | ACK 后才移除本地操作；断网恢复后补传 |
| 首页 | 有容量与 TTL 的 SQLite 缓存，先显示缓存 | 版本化日结果 | 首页不等待 182 天详细曲线 |
| 历史 | 近期详情 + 访问过的日期详情 + 日摘要 | 完整日结果、变化版本、按日期详情 | 摘要增量读；选择日期才读取详情 |
| 营养 / 夜间 HRV 等正式指标 | 同一结果的 UI 缓存 | `metric-read` / `metric.query` 共用指标定义 | 显式日期、单位、缺失和版本；不把无数据当零 |
| AI 分析 | 发送待上传数量和分域状态；最多等待 3 秒 | 用户 JWT + RLS 下的只读工具 | 可继续查询多个领域；同次请求复用证据；历史对话不充当当前测量 |
| 对话 | 现有本地聊天归档 | 独立 conversations/messages 与有界原文摘要 | 会话 ID 隔离；近期消息与较早用户原文作为上下文 |
| 超过热窗口的细粒度证据 | 不新增永久全量副本 | 私有 Storage 压缩对象 + 校验清单 | 热冷共享读取；校验恢复成功后才清理热记录 |
| 运行跟踪 | 不重复缓存完整工具数据 | ai_turns 单份 trace，frame 引用；独立业务会话 | 业务会话不依赖会过期的 frame |

## 发布顺序

1. 备份并在预发布环境按文件名顺序应用本次 migration；包括 ingestion、calculation、conversation/meal receipts、archive/hydration/recovery 和 request budget。不要只部署前端。
2. 部署 `metric-read`、`meal-commit`、`meal-operation`、`turn`、`archive-data`、`export`、`account-delete` 及共享模块。验证旧客户端仍可使用原有读取和入库契约。
3. 发布 App。旧缓存只有成功写入并重新读回 SQLite 后才删除。旧历史空版本号仍会被读取，不要求先重算整个历史。
4. 按 [归档运行说明](../../supabase/functions/archive-data/README.md) 配置受认证的定时归档。每批有上限；需监控失败与积压，未验证归档不得删热数据。
5. 对需要冷数据重算的账号重复执行受限恢复批次，直到 ready；上线前已永久丢失的原始数据会明确报告，不能重建或伪造。

已有热原始数据 400 天、渲染 frame 90 天、分析事件 180 天的保留窗口不缩短。冷归档不自动到期。删除账号包含新表、对象和本地待上传操作；普通退出保留按账号隔离的待上传记录。

针对性测试覆盖日期解析、指标/证据一致性、缓存与队列、迟到采样、版本化重算、归档恢复、对话持久化及账号生命周期。最终测试汇总与性能工作负载另附；不能把 SQL 耗时当成真机首屏或外部模型响应延迟。

尚须在预发布与真机进行发布验收：杀进程后恢复离线操作、BLE 实际补读、弱网首屏、迁移后的多账号切换以及真实模型多轮查询。生产部署、定时调度启用和生产清理均未执行。
